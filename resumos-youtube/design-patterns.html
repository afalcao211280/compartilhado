Resumo — "6 Design Patterns que você vai usar no dia a dia"

Fonte: youtube.com/watch?v=G-O90vR7SCU  •  vídeo em pt-BR, ~10:46  •  resumo em 30/08/2026
O que são Design Patterns: soluções reutilizáveis para problemas que aparecem toda hora na construção de software. Analogia do vídeo: a planta de uma casa — você não inventa do zero como construir uma cozinha toda vez que projeta uma casa. O termo ficou famoso em 1994 (Gang of Four, 23 padrões), mas na prática uns 6 são muito mais usados que os outros.

1.Observer — "reagir a mudanças"

Problema: vários objetos precisam ser notificados quando algo muda, sem ficarem checando o tempo todo.

Exemplo do vídeo (YouTube)
Você se inscreve no canal e ativa o sino. Toda vez que o canal posta vídeo novo, você recebe a notificação — não precisa entrar no canal toda hora. Subject = o canal (mantém a lista de observers); Observers = inscritos. Quando o estado muda, o subject percorre a lista e chama update/notify em cada um. Estrutura: on registra, emit notifica todos.
Exemplos reais (você já usa todo dia)
addEventListener do DOM • EventEmitter do Node.js • useEffect do React (reage quando uma dependência muda)

Quando usar: o desacoplamento é o motivo — o subject não precisa saber quem está escutando nem quantos observers existem. Útil quando módulos diferentes precisam reagir ao mesmo evento.

2.Factory — "criar objetos de forma flexível"

Problema: criação de objetos complexa ou variável por contexto, com lógica espalhada no código.

Exemplo do vídeo (pizzaria)
Você pede uma marguerita e não entra na cozinha pra escolher massa, preparar molho e montar a pizza. Você só diz o que quer e a cozinha entrega. Quem pede o objeto não precisa saber como ele é construído — a criação é delegada a um método/classe especializada.
Exemplo de código (sistema de pagamentos)
Pix, cartão ou boleto, cada um com lógica específica. Sem factory: switch no meio do código, lógica espalhada. Com factory: tudo centralizado e isolado — o resto do código nem sabe qual classe é usada, e um novo tipo de pagamento muda num lugar só.
Exemplos reais
document.createElement no browser • Jest usa factories para criar mocks • frameworks que instanciam componentes

3.Singleton — "garantir instância única" ⚠ polêmico

Problema: um objeto precisa existir exatamente uma vez no sistema inteiro.

Exemplo do vídeo (prédio)
Um prédio de vários andares tem um elevador — todo mundo usa o mesmo. Não faz sentido ter um diferente pra cada andar.
Mecânica
Constructor privado — ninguém dá new Database direto. Única forma de obter: getInstance(). 1ª chamada cria; as seguintes retornam a mesma instância. Módulo de usuários, pedidos ou relatórios: todos recebem a mesma conexão com o banco.
⚠ Por que é polêmico
Muita gente considera antipattern: cria estado global que dificulta testes e esconde dependências. Em frameworks atuais, o singleton costuma vir do container de injeção de dependências — o framework garante a instância única sem acoplar o código. Recomendado apenas para: pool de conexão com o banco, configuração da aplicação, sistema de logs.

4.Decorator — "adicionar comportamento sem modificar o objeto"

Problema: adicionar responsabilidades a um objeto de forma dinâmica, sem alterar o objeto original.

Exemplo do vídeo (filtros do Instagram)
Foto + filtro, depois contraste, depois brilho. Cada filtro recebe a imagem anterior e devolve uma nova versão com o efeito aplicado — a foto original continua intacta. Entrada e saída são sempre uma imagem, então dá pra empilhar quantos filtros quiser, na ordem que quiser.
Exemplo de código (sistema de notificações)
Começa com e-mail, precisa de Slack, depois SMS. Em vez de uma classe Deus gigante: SlackDecorator recebe um Notifier no constructor, chama o send() original e adiciona a lógica do Slack. Uso: vai encadeando — quer só e-mail e SMS sem Slack? Não adiciona o decorator.
Exemplos reais
Decorators do TypeScript (@) • @Injectable do Angular • @Component do NestJS

5.Strategy — "trocar algoritmos em tempo de execução"

Problema: um problema resolvível de várias formas, com troca de solução sem mudar o resto do código.

Exemplo do vídeo (GPS)
Carro, bicicleta ou transporte público — cada opção usa um algoritmo diferente para calcular a rota, mas a interface é a mesma: você só escolhe qual estratégia quer.
Exemplo de código
A classe Sorter não sabe qual algoritmo usa — só sabe que tem um objeto com método sort(). Troca a qualquer momento com setStrategy(). Validação de formulários: CPF, telefone e senha têm lógicas diferentes — em vez de if/else gigante, cada regra vira um strategy.
Exemplos reais
Middleware do Express (escolhe o render) • estratégias de autenticação do Passport • função comparadora do Array.sort() do JS

Detalhe: estratégia com estado ou vários métodos → classe. Operação simples → função resolve.

6.Adapter — "conectar interfaces incompatíveis"

Problema: usar biblioteca ou API externa cuja interface não encaixa no seu código, sem refatorar tudo.

Exemplo do vídeo (adaptador de tomada)
Carregador funciona, tomada funciona, mas são incompatíveis. O adaptador não muda o carregador nem a tomada — só faz a conexão entre eles.
Exemplo de código (API externa)
API retorna first_name/last_name, seu sistema usa nome/sobrenome. Não muda a API nem o sistema → cria um adapter: os dados entram num formato e saem no esperado. O adapter é a cola entre duas interfaces incompatíveis.
Exemplo de código (migração de biblioteca)
Sistema inteiro usa axios, quer trocar pro fetch nativo. Em vez de mudar centenas de arquivos, um adapter implementa a mesma interface do axios usando fetch por baixo. O resto do código nem percebe — interface igual, implementação diferente.
Exemplos reais
ORMs (Prisma, TypeORM) são adapters entre seu código e o banco • drivers de banco traduzem chamadas genéricas pro protocolo de cada banco

Resumo rápido: qual usar quando

Patterns interagem entre si

Combinações do mundo real:
  • Um factory pode criar singletons
  • Um observer pode usar strategy para decidir como notificar
  • Um adapter pode envolver um objeto criado por uma factory
Conforme você conhece os padrões, começa a enxergar as combinações.
Aviso final do vídeo
Não saia enfiando design pattern em tudo. Eles existem para resolver problemas reais, não para deixar o código bonito. Se o problema não existe, o pattern também não precisa ser usado.

Exemplos de código — Java 26 e Go 1.26

Os 6 padrões implementados com recursos atuais das duas linguagens (Java: records, sealed interfaces, pattern matching com switch, lambdas — Go 1.21+ com sync.OnceValue, interfaces funcionais implícitas, empacotamento com structs). Todos os 12 exemplos compilam e rodam: saída validada acima.

Observer

Eventos do DOM, WebHooks, sistemas reativos — o canal notifica os inscritos sem saber quem são.

// Java 26 — Observer (lambdas)
import java.util.ArrayList;
import java.util.List;
import java.util.function.Consumer;

// Observer: interface funcional
interface Subscriber {
    void notify(String title);
}

class Channel {
    private final List<Subscriber> subscribers
        = new ArrayList<>();

    public void subscribe(Subscriber s) {
        subscribers.add(s);
    }

    // Emit: notifica todos os observers
    public void publish(String title) {
        System.out.println("Canal postou: " + title);
        subscribers.forEach(s -> s.notify(title));
    }
}

public class ObserverDemo {
    public static void main(String[] args) {
        Channel ch = new Channel();

        // Lambdas como observers
        ch.subscribe(title ->
            System.out.println("Alice: " + title));
        ch.subscribe(title ->
            System.out.println("Bob: " + title));

        ch.publish("Design Patterns!");
    }
}
// Go 1.26 — Observer (funcoes como subscribers)
package main

import "fmt"

// Observer: interface com 1 metodo = func
type Subscriber func(title string)

type Channel struct {
    subscribers []Subscriber
}

func (c *Channel) Subscribe(s Subscriber) {
    c.subscribers = append(c.subscribers, s)
}

// Emit: notifica todos os observers
func (c *Channel) Publish(title string) {
    fmt.Println("Canal postou:", title)
    for _, s := range c.subscribers {
        s(title)
    }
}

func main() {
    ch := &Channel{}

    alice := func(t string) {
        fmt.Println("Alice recebeu:", t)
    }
    bob := func(t string) {
        fmt.Println("Bob recebeu:", t)
    }

    ch.Subscribe(alice)
    ch.Subscribe(bob)

    ch.Publish("Design Patterns em Go!")
}
# Python 3.14 — Observer (Protocol)
from typing import Protocol

class Subscriber(Protocol):
    def notify(self, title: str) -> None: ...


class Channel:
    def __init__(self) -> None:
        self._subscribers: list[Subscriber] = []

    def subscribe(self, s: Subscriber) -> None:
        self._subscribers.append(s)

    # Emit: notifica todos os observers
    def publish(self, title: str) -> None:
        print(f"Canal postou: {title}")
        for s in self._subscribers:
            s.notify(title)


class Alice:
    def notify(self, title: str) -> None:
        print(f"Alice recebeu: {title}")


class Bob:
    def notify(self, title: str) -> None:
        print(f"Bob recebeu: {title}")


if __name__ == "__main__":
    ch = Channel()
    ch.subscribe(Alice())
    ch.subscribe(Bob())
    ch.publish("Design Patterns em Python!")

Factory

Pagamentos Pix/cartão/boleto — a criação fica centralizada e isolada; se aparecer um tipo novo, muda num lugar só.

// Java 26 — Factory (records + sealed + switch)
import java.util.function.Supplier;

// Produtos: os tipos de pagamento
sealed interface Payment
    permits Pix, Cartao, Boleto {
    String process();
}

record Pix(String chave) implements Payment {
    public String process() {
        return "PIX: " + chave;
    }
}

record Cartao(String numero,
    String bandeira) implements Payment {
    public String process() {
        return "Cartao " + bandeira
            + ": " + numero;
    }
}

record Boleto(String codigo) implements Payment {
    public String process() {
        return "Boleto: " + codigo;
    }
}

// Factory: quem chama nao sabe a classe
final class PaymentFactory {
    private PaymentFactory() {}

    static Payment create(String tipo,
        String payload) {
        return switch (tipo) {
            case "pix" -> new Pix(payload);
            case "cartao" ->
                new Cartao(payload, "VISA");
            case "boleto" ->
                new Boleto(payload);
            default -> throw new
                IllegalArgumentException(
                "tipo desconhecido: " + tipo);
        };
    }
}

public class FactoryDemo {
    public static void main(String[] args) {
        Payment p = PaymentFactory.create(
            "pix", "alice@email.com");
        System.out.println(p.process());

        Payment c = PaymentFactory.create(
            "cartao", "4111-1111");
        System.out.println(c.process());
    }
}
// Go 1.26 — Factory (interface + switch)
package main

import "fmt"

// Produtos: os tipos de pagamento
type Payment interface {
    Process() string
}

type Pix struct{ Chave string }

func (p Pix) Process() string {
    return "PIX: " + p.Chave
}

type Cartao struct{ Numero, Bandeira string }

func (c Cartao) Process() string {
    return "Cartao " + c.Bandeira +
        ": " + c.Numero
}

type Boleto struct{ Codigo string }

func (b Boleto) Process() string {
    return "Boleto: " + b.Codigo
}

// Factory centraliza a criacao — quem
// chama nao sabe a classe concreta
func NewPayment(tipo, payload string) (
    Payment, error) {
    switch tipo {
    case "pix":
        return Pix{Chave: payload}, nil
    case "cartao":
        return Cartao{Numero: payload,
            Bandeira: "VISA"}, nil
    case "boleto":
        return Boleto{Codigo: payload}, nil
    default:
        return nil, fmt.Errorf(
            "tipo desconhecido: %s", tipo)
    }
}

func main() {
    p, _ := NewPayment("pix",
        "alice@email.com")
    fmt.Println(p.Process())

    c, _ := NewPayment("cartao", "4111-1111")
    fmt.Println(c.Process())
}
# Python 3.14 — Factory (dataclasses + match)
from dataclasses import dataclass
from typing import Protocol

class Payment(Protocol):
    def process(self) -> str: ...


@dataclass(frozen=True)
class Pix:
    chave: str

    def process(self) -> str:
        return f"PIX: {self.chave}"


@dataclass(frozen=True)
class Cartao:
    numero: str
    bandeira: str

    def process(self) -> str:
        return f"Cartao {self.bandeira}: {self.numero}"


@dataclass(frozen=True)
class Boleto:
    codigo: str

    def process(self) -> str:
        return f"Boleto: {self.codigo}"


# Factory: quem chama nao sabe a classe concreta
class PaymentFactory:
    @staticmethod
    def create(tipo: str, payload: str) -> Payment:
        match tipo:  # pattern matching (Python 3.10+)
            case "pix":
                return Pix(chave=payload)
            case "cartao":
                return Cartao(numero=payload, bandeira="VISA")
            case "boleto":
                return Boleto(codigo=payload)
            case _:
                raise ValueError(f"tipo desconhecido: {tipo}")


if __name__ == "__main__":
    p = PaymentFactory.create("pix", "alice@email.com")
    print(p.process())  # PIX: alice@email.com

    c = PaymentFactory.create("cartao", "4111-1111")
    print(c.process())  # Cartao VISA: 4111-1111

Singleton

Uma conexão de banco para o sistema inteiro — mas cuidado: estado global dificulta testes; em frameworks atuais quem garante a instância única é o container de injeção de dependência.

// Java 26 — Singleton (holder idiom)
// Holder idiom: criacao lazy, thread-safe,
// sem synchronized
final class Database {
    private Database() {
        System.out.println(
            "Conectando ao banco...");
    }

    private static final class Holder {
        private static final Database INSTANCE
            = new Database();
    }

    static Database getInstance() {
        return Holder.INSTANCE;
    }

    void query(String sql) {
        System.out.println("Executando: " + sql);
    }
}

public class SingletonDemo {
    public static void main(String[] args) {
        Database d1 = Database.getInstance();
        Database d2 = Database.getInstance();

        System.out.println("Mesma instancia? "
            + (d1 == d2));
        d1.query("SELECT 1");
    }
}
// Go 1.26 — Singleton (sync.OnceValue)
package main

import (
    "fmt"
    "sync"
)

type Database struct{}

func NewDatabase() *Database {
    fmt.Println("Conectando ao banco...")
    return &Database{}
}

func (d *Database) Query(sql string) {
    fmt.Println("Executando:", sql)
}

// Go 1.21+: cria exatamente uma vez,
// thread-safe, retorna sempre a mesma
// instancia
var dbOnce = sync.OnceValue(NewDatabase)

func GetDatabase() *Database {
    return dbOnce()
}

func main() {
    d1 := GetDatabase()
    d2 := GetDatabase()

    fmt.Println("Mesma instancia?", d1 == d2)
    d1.Query("SELECT 1")
}
# Python 3.14 — Singleton (__new__ + lock)
from threading import Lock
from typing import ClassVar


class Database:
    _instance: ClassVar["Database | None"] = None
    _lock: ClassVar[Lock] = Lock()

    def __new__(cls) -> "Database":
        if cls._instance is None:
            with cls._lock:
                if cls._instance is None:
                    print("Conectando ao banco...")
                    cls._instance = super().__new__(cls)
        return cls._instance

    def query(self, sql: str) -> None:
        print(f"Executando: {sql}")


if __name__ == "__main__":
    d1 = Database()
    d2 = Database()

    print("Mesma instancia?", d1 is d2)  # True
    d1.query("SELECT 1")

Decorator

Notificações por e-mail + Slack + SMS — empilha camadas sem criar uma classe gigante; quer só email e SMS? É só não envolver com o SlackDecorator.

// Java 26 — Decorator (records)
interface Notifier {
    void send(String msg);
}

record EmailNotifier() implements Notifier {
    public void send(String msg) {
        System.out.println("Email: " + msg);
    }
}

// Decorator: embrulha o anterior, chama o
// original e adiciona comportamento
record SlackDecorator(Notifier wrapped)
    implements Notifier {
    public void send(String msg) {
        wrapped.send(msg);
        System.out.println("Slack: " + msg);
    }
}

record SMSDecorator(Notifier wrapped)
    implements Notifier {
    public void send(String msg) {
        wrapped.send(msg);
        System.out.println("SMS: " + msg);
    }
}

public class DecoratorDemo {
    public static void main(String[] args) {
        // Empilhando decorators
        Notifier n = new SlackDecorator(
            new SMSDecorator(
                new EmailNotifier()));
        n.send("Compra aprovada");

        // So email + SMS:
        Notifier simples = new SMSDecorator(
            new EmailNotifier());
        simples.send("Cupom de desconto");
    }
}
// Go 1.26 — Decorator (structs)
package main

import "fmt"

type Notifier interface {
    Send(msg string)
}

type EmailNotifier struct{}

func (EmailNotifier) Send(msg string) {
    fmt.Println("Email:", msg)
}

// Decorator: embrulha o anterior, chama o
// original e adiciona comportamento
type SlackDecorator struct {
    wrapped Notifier
}

func (d SlackDecorator) Send(msg string) {
    d.wrapped.Send(msg)
    fmt.Println("Slack:", msg)
}

type SMSDecorator struct {
    wrapped Notifier
}

func (d SMSDecorator) Send(msg string) {
    d.wrapped.Send(msg)
    fmt.Println("SMS:", msg)
}

func main() {
    // Empilhando decorators — objeto
    // original intacto, efeitos em camadas
    n := SlackDecorator{
        wrapped: SMSDecorator{
            wrapped: EmailNotifier{}}}
    n.Send("Compra aprovada")

    // So email + SMS? Sem SlackDecorator
    simples := SMSDecorator{
        wrapped: EmailNotifier{}}
    simples.Send("Cupom de desconto")
}
# Python 3.14 — Decorator (classes empilháveis)
from typing import Protocol

class Notifier(Protocol):
    def send(self, msg: str) -> None: ...


class EmailNotifier:
    def send(self, msg: str) -> None:
        print(f"Email: {msg}")


# Decorator: embrulha o anterior, chama o original e adiciona
class SlackDecorator:
    def __init__(self, wrapped: Notifier) -> None:
        self._wrapped = wrapped

    def send(self, msg: str) -> None:
        self._wrapped.send(msg)
        print(f"Slack: {msg}")


class SMSDecorator:
    def __init__(self, wrapped: Notifier) -> None:
        self._wrapped = wrapped

    def send(self, msg: str) -> None:
        self._wrapped.send(msg)
        print(f"SMS: {msg}")


if __name__ == "__main__":
    # Empilhando decorators (email -> sms -> slack)
    n = SlackDecorator(SMSDecorator(EmailNotifier()))
    n.send("Compra aprovada")

    # So email + SMS? Sem SlackDecorator
    simples = SMSDecorator(EmailNotifier())
    simples.send("Cupom de desconto")

Strategy

Validação de formulários / ordenação — troca o algoritmo em tempo de execução sem mudar o resto do código.

// Java 26 — Strategy (lambda como strategy)
import java.util.Arrays;
import java.util.Comparator;

// Estrategia = interface funcional
interface SortingStrategy {
    void sort(int[] data);
}

// Cada algoritmo encapsulado
// em sua propria classe
final class BubbleSort
    implements SortingStrategy {
    public void sort(int[] data) {
        for (int i = 0; i < data.length; i++) {
            for (int j = 0;
                j < data.length - 1 - i; j++) {
                if (data[j] > data[j + 1]) {
                    int tmp = data[j];
                    data[j] = data[j + 1];
                    data[j + 1] = tmp;
                }
            }
        }
    }
}

final class Sorter {
    private SortingStrategy strategy;

    void setStrategy(SortingStrategy s) {
        strategy = s;
    }

    void run(int[] data) {
        strategy.sort(data);
    }
}

public class StrategyDemo {
    public static void main(String[] args) {
        Sorter s = new Sorter();

        // Estrategia nativa
        int[] a = {5, 3, 8, 1};
        s.setStrategy(Arrays::sort);
        s.run(a);
        System.out.println(
            Arrays.toString(a));

        // Lambda como strategy
        int[] b = {9, 2, 7};
        s.setStrategy(data -> {
            var wrapped = Arrays.stream(data)
                .boxed()
                .toArray(Integer[]::new);
            Arrays.sort(wrapped,
                Comparator.naturalOrder());
            for (int i = 0; i < data.length; i++)
                data[i] = wrapped[i];
        });
        s.run(b);
        System.out.println(
            Arrays.toString(b));
    }
}
// Go 1.26 — Strategy (func = strategy)
package main

import (
    "fmt"
    "sort"
)

// Estrategia = funcao com a mesma
// assinatura
type SortStrategy func([]int)

type Sorter struct {
    strategy SortStrategy
}

func (s *Sorter) SetStrategy(
    st SortStrategy) {
    s.strategy = st
}

func (s *Sorter) Run(data []int) {
    s.strategy(data)
}

func bubbleSort(data []int) {
    for i := range data {
        for j := 0; j < len(data)-1-i; j++ {
            if data[j] > data[j+1] {
                data[j], data[j+1] =
                    data[j+1], data[j]
            }
        }
    }
}

func main() {
    s := &Sorter{}

    // Troca de estrategia em tempo de
    // execucao, sem mudar o Sorter
    a := []int{5, 3, 8, 1}
    s.SetStrategy(sort.Ints)
    s.Run(a)
    fmt.Println(a)

    b := []int{9, 2, 7}
    s.SetStrategy(bubbleSort)
    s.Run(b)
    fmt.Println(b)
}
# Python 3.14 — Strategy (callable como estrategia)
from collections.abc import Callable

# type alias (PEP 695, Python 3.12+)
type SortStrategy = Callable[[list[int]], None]


class Sorter:
    def __init__(self) -> None:
        self._strategy: SortStrategy | None = None

    def set_strategy(self, strategy: SortStrategy) -> None:
        self._strategy = strategy

    def run(self, data: list[int]) -> None:
        assert self._strategy is not None
        self._strategy(data)


def bubble_sort(data: list[int]) -> None:
    n = len(data)
    for i in range(n):
        for j in range(n - 1 - i):
            if data[j] > data[j + 1]:
                data[j], data[j + 1] = data[j + 1], data[j]


def py_sort(data: list[int]) -> None:
    data.sort()


if __name__ == "__main__":
    s = Sorter()

    # Troca de estrategia em tempo de execucao
    a = [5, 3, 8, 1]
    s.set_strategy(py_sort)
    s.run(a)
    print(a)  # [1, 3, 5, 8]

    b = [9, 2, 7]
    s.set_strategy(bubble_sort)
    s.run(b)
    print(b)  # [2, 7, 9]

Adapter

API externa retorna first_name/last_name, mas seu sistema usa nome/sobrenome — o adapter é a cola entre duas interfaces incompatíveis; o resto do código nem percebe.

// Java 26 — Adapter (records)
// Formato da API externa — nao mudar
record ExternalUser(String firstName,
    String lastName, String email) {}

// Formato do nosso sistema
record User(String nome, String sobrenome,
    String email) {}

// Interface que o sistema espera
interface UserClient {
    User findByID(String id);
}

// API externa simulada
final class ExternalUserAPI {
    ExternalUser fetch(String id) {
        return new ExternalUser(
            "Joao", "Silva",
            "joao@email.com");
    }
}

// Adapter: a cola entre as duas
// interfaces incompativeis
final class UserAdapter
    implements UserClient {
    private final ExternalUserAPI api
        = new ExternalUserAPI();

    public User findByID(String id) {
        ExternalUser ext = api.fetch(id);
        return new User(ext.firstName(),
            ext.lastName(), ext.email());
    }
}

public class AdapterDemo {
    public static void main(String[] args) {
        // O sistema so conhece UserClient
        UserClient client = new UserAdapter();

        User u = client.findByID("1");
        System.out.printf("%s %s <%s>%n",
            u.nome(), u.sobrenome(), u.email());
    }
}

package main

import "fmt"

// Formato da API externa (JSON tags) —
// nao podemos mudar
type ExternalUser struct {
    FirstName string `json:"first_name"`
    LastName  string `json:"last_name"`
    Email     string `json:"email"`
}

// Formato do nosso sistema
type User struct {
    Nome, Sobrenome, Email string
}

// Interface que o sistema espera
type UserClient interface {
    FindByID(id string) (*User, error)
}

// API externa simulada
type ExternalUserAPI struct{}

func (ExternalUserAPI) Fetch(id string)
    ExternalUser {
    return ExternalUser{
        FirstName: "Joao",
        LastName:  "Silva",
        Email:     "joao@email.com",
    }
}

// Adapter: a cola entre as duas
// interfaces incompativeis
type UserAdapter struct {
    api ExternalUserAPI
}

func (a UserAdapter) FindByID(
    _ string) (*User, error) {
    ext := a.api.Fetch("1")
    return &User{
        Nome:      ext.FirstName,
        Sobrenome: ext.LastName,
        Email:     ext.Email,
    }, nil
}

func main() {
    // O sistema so conhece a interface
    var client UserClient = UserAdapter{}

    u, err := client.FindByID("1")
    if err != nil {
        panic(err)
    }
    fmt.Printf("%s %s <%s>\\n",
        u.Nome, u.Sobrenome, u.Email)
}
# Python 3.14 — Adapter (dataclasses + Protocol)
from dataclasses import dataclass
from typing import Protocol

# Formato da API externa — nao mudar
@dataclass(frozen=True)
class ExternalUser:
    first_name: str
    last_name: str
    email: str


# Formato do nosso sistema
@dataclass(frozen=True)
class User:
    nome: str
    sobrenome: str
    email: str


# Interface que o sistema espera
class UserClient(Protocol):
    def find_by_id(self, user_id: str) -> User: ...


# API externa simulada
class ExternalUserAPI:
    def fetch(self, user_id: str) -> ExternalUser:
        return ExternalUser("Joao", "Silva", "joao@email.com")


# Adapter: a cola entre as duas interfaces incompativeis
class UserAdapter:
    def __init__(self, api: ExternalUserAPI | None = None) -> None:
        self._api = api or ExternalUserAPI()

    def find_by_id(self, user_id: str) -> User:
        ext = self._api.fetch(user_id)
        return User(nome=ext.first_name, sobrenome=ext.last_name, email=ext.email)


if __name__ == "__main__":
    # O sistema so conhece a interface
    client: UserClient = UserAdapter()

    u = client.find_by_id("1")
    print(f"{u.nome} {u.sobrenome} <{u.email}>")
