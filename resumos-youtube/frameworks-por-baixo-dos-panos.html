O que React, Vue e Angular fazem por baixo dos panos

Resumo em pt-BR · vídeo ~12:48 · ver no YouTube · 30/08/2026
Você usa React, Vue ou Angular todo dia — mas sabe o que esses frameworks fazem por baixo dos panos? Os 10 conceitos internos explicam comportamentos estranhos e bugs comuns que você já encontrou.

10.Gerenciamento de estado

Todo framework resolve como os dados fluem entre componentes.

  • Prop drilling: dado no raiz, consumo 5 níveis abaixo → passar por intermediários que nem usam. Solução: canal direto entre quem produz e quem consome (context/store/provide-inject)
  • Estado local (input, item selecionado) fica no componente e morre com ele
  • Estado global (usuário logado, tema, carrinho) para dados de vários componentes
  • Colocar tudo no global → rerenderiza o que não precisava atualizar
Valor derivado
Se algo pode ser calculado de outro estado (ex.: filtrados a partir de itens + filtro), não crie estado novo — apenas derive. Estado duplicado → esqueceu de atualizar → ficam dessincronizados.

9.Agrupamento de atualizações (batching)

Clicou num botão e mudou 3 estados (nome, e-mail, endereço):

  • Sem batching: renderizaria o componente 3 vezes
  • Com batching: coleta as mudanças numa fila e processa tudo junto — DOM atualizado uma vez com o resultado final
Pegadinha
Mudou estado e tentou ler o DOM logo em seguida → valor ainda é o antigo (o DOM só atualiza depois que o framework processa a fila).

8.Tree shaking e code splitting

O bundler junta todos os arquivos JS num pacote — app grande pode passar de 2 MB, e o usuário baixa tudo antes de ver qualquer coisa.

  • Tree shaking: remove funções/módulos não importados. Lodash inteiro = 70 KB; só debounce = 2 KB. Import de forma específica ajuda mais ainda
  • Code splitting: divide o bundle — Home baixa só o JS da Home, Dashboard só o chunk do Dashboard. Componente lazy baixa só quando precisa

Tree shaking remove código morto; code splitting divide o código vivo em pedaços menores.

7.Ciclo de vida do componente

Três fases: monta (aparece), atualiza (estado/props mudam), desmonta (sai da tela). Cada framework dá hooks para essas fases.

Cleanup é essencial
Chat que abre WebSocket ao montar precisa fechar ao desmontar. Trocar de sala 3 vezes sem cleanup = 3 conexões abertas. Timers, listeners e conexões que nunca fecham acumulam lixo na memória.

6.Compilação

O navegador não entende JSX, templates ou extensões próprias — tudo é transformado em JS puro no build:

  • Templates viram instruções de DOM, expressões viram lógica de atualização
  • Tradeoff: mais runtime no navegador (flexibilidade em runtime) vs mais trabalho no compilador (instruções específicas por componente, quase nada de runtime)

5.Roteamento no cliente

  • Site tradicional: clicou no link → requisição ao servidor → HTML novo → renderiza do zero (pisca, perde estado, ~meio segundo)
  • SPA: JS intercepta o clique, atualiza a URL e troca o conteúdo — sem requisição, praticamente instantâneo
  • Por baixo: History API — pushState muda a URL sem requisição; popstate dispara no voltar
Problema
Digitar site.com/produtos direto → o servidor precisa devolver index.html para todas as rotas, senão 404 (fallback de rota).

4.Hydration

Com SSR, o servidor manda HTML completo → o usuário vê a página quase instantânea, mas estática. O JS carrega e conecta event listeners e estado a cada elemento — isso é hydration.

  • Vantagem: conteúdo visível antes do JS carregar (conexão lenta = usuário fica)
  • Divergência de hydration: HTML do servidor ≠ JS do cliente → framework reclama ou renderiza tudo de novo (perde a vantagem do SSR)
  • Arquitetura de ilhas: página quase toda em HTML puro; só os componentes interativos recebem hydration → menos JS, carrega mais rápido

3.Sistema de reatividade

Como o framework descobre o que mudou quando o estado muda?

AbordagemComo funcionaQuando brilha
Virtual DOMcria cópia da árvore, compara com a antiga, aplica só as diferenças no DOMmaioria das aplicações
Signalssabe qual variável está ligada a qual elemento — vai direto no alvo, sem difflistas grandes, animações pesadas

Signals podem rodar em runtime (proxies) ou em tempo de compilação (gerando JS que já sabe quais instruções de DOM executar).

2.Reconciliação

Algoritmo que descobre o que mudou entre um render e outro:

  • Tipo mudou (div → span): destrói o antigo e cria novo do zero
  • Mesmo tipo: só atualiza as props que mudaram
  • Listas precisam de key: sem key compara por posição — deletou o item do meio → acha que os últimos mudaram e recria
  • Com key compara por identidade — só o item removido sai
Erro mais comum
Usar o index como key. Só funciona em lista estática; ao adicionar/remover/reordenar, o framework confunde componentes, inputs perdem texto, animações resetam, estado vaza. Para resetar um componente de propósito, basta mudar a key (remonta do zero).

1.O DOM (a base de tudo)

O navegador transforma HTML numa árvore de objetos na memória — cada tag vira um nó com propriedades, métodos e relações. JavaScript interage com a página através do DOM: querySelector acessa um objeto na memória; textContent atualiza a tela.

  • Cada mudança no DOM tem custo: recalcular estilos, recalcular layout, repintar pixels
  • Mudanças em sequência deixam o navegador lento
  • Frameworks existem para minimizar quantas vezes o DOM é tocado — reconciliação, reatividade, batching — e para você ser produtivo (estado, ciclo de vida, routing)

Exemplos de código — React + Next, Vue e Angular

3 conceitos com componentes nos formatos canônicos de cada framework. Lógica validada executando num contexto Node — as 3 stacks produzem a mesma saída.

Estado derivado — sem estado duplicado

// React + Next (App Router)
'use client';
import { useMemo, useState } from 'react';

export default function ProductList({ items }) {
  const [query, setQuery] = useState('');
  // filtrados é DERIVADO
  // (items + query) — não é estado
  const filtered = useMemo(
    () => items.filter((it) =>
      it.name.toLowerCase().includes(
        query.toLowerCase())),
    [items, query],
  );
  return (
    <>
      <input value={query}
        onChange={(e) =>
          setQuery(e.target.value)} />
      <ul>{filtered.map((it) =>
        <li key={it.id}>
          {it.name}</li>)}</ul>
    </>
  );
}

// Vue (Composition API)
<script setup>
import { ref, computed } from 'vue';

const props =
  defineProps({ items: Array });
const query = ref('');

// filtrados é DERIVADO
// (items + query) — não é estado
const filtered = computed(() =>
  props.items.filter((it) =>
    it.name.toLowerCase().includes(
      query.value.toLowerCase())));
</script>

<template>
  <input v-model="query" />
  <ul><li v-for="it in filtered"
    :key="it.id">
    {{ it.name }}</li></ul>
</template>

// Angular (standalone + signals)
import { Component, computed,
  signal } from '@angular/core';

@Component({
  selector: 'app-product-list',
  template: `
    <input [value]="query()"
      (input)="query.set(
        $any($event.target).value)" />
    <ul>
      <li *ngFor="let it of filtered();
        trackBy: trackById"
        {{ it.name }}</li>
    </ul>
  `,
  standalone: true,
})
export class ProductListComponent {
  query = signal('');
  items = signal([...]);
  // filtrados é DERIVADO
  // (computed) — não é estado
  filtered = computed(() =>
    this.items().filter((it) =>
      it.name.toLowerCase().includes(
        this.query().toLowerCase())));

  trackById(_i: number,
    it: { id: number }) {
    return it.id; }
}

Ciclo de vida — cleanup de conexão (WebSocket)

// React
'use client';
import { useEffect } from 'react';

export default function ChatRoom({ roomId }) {
  useEffect(() => {
    const ws = connect(roomId);
    // montou -> abre conexao
    return () => ws.close();
    // desmontou -> fecha (cleanup)
  }, [roomId]);
  // trocou sala -> abre/fecha de novo
  return <div className="chat">…</div>;
}

// Vue
<script setup>
import { onMounted, onUnmounted }
  from 'vue';

const props =
  defineProps({ roomId: String });
let ws;

onMounted(() => {
  // montou -> abre conexao
  ws = connect(props.roomId);
});
onUnmounted(() => ws.close());
// desmontou -> fecha
</script>

<template>
  <div className="chat">…</div>
</template>

// Angular
import { Component, DestroyRef,
  inject } from '@angular/core';

@Component({
  selector: 'app-chat-room',
  template: `<div class="chat">…</div>`,
  standalone: true,
})
export class ChatRoomComponent {
  private ws: any;
  private destroyRef =
    inject(DestroyRef);

  constructor() {
    // montou -> abre conexao
    this.ws =
      connect(this.roomId);
    // desmontou -> fecha
    this.destroyRef.onDestroy(
      () => this.ws.close());
  }
}

Reconciliação — key / trackBy (identidade vs posição)

React — key
<ul>
  {items.map((it) => (
    <li key={it.id}>
      {it.name}</li>
  ))}
</ul>
// ERRADO: key={index}
// quebra ao adicionar/
// remover/reordenar

// diff SEM key (posicao):
//  atualiza pos 1:
//    Bruno -> Carla
//  remove Carla da pos 2

// diff COM key (id):
//  remove Bruno
//  move Carla p/ pos 1

Vue — :key
<ul>
  <li v-for="it in items"
    :key="it.id">
    {{ it.name }}</li>
</ul>
<!-- ERRADO: :key="index"
   so funciona em lista
   estatica -->

// diff SEM :key (posicao):
//  atualiza pos 1:
//    Bruno -> Carla
//  remove Carla da pos 2

// diff COM :key (id):
//  remove Bruno
//  move Carla p/ pos 1

Angular — trackBy
// template: *ngFor=
//   "let it of items;
//    trackBy: trackById"
trackById(_index: number,
  it: { id: number }) {
  return it.id;
}
// ERRADO: sem trackBy
// compara por posicao

// diff SEM trackBy:
//  atualiza pos 1:
//    Bruno -> Carla
//  remove Carla da pos 2

// diff COM trackBy:
//  remove Bruno
//  move Carla p/ pos 1

Saída validada do diff (idêntica nas 3): sem key → atualiza pos 1: Bruno -> Carla; com key → remove Bruno e move Carla p/ pos 1. Sem key o framework acha que Carla mudou (perde estado/input); com key só Bruno sai.
